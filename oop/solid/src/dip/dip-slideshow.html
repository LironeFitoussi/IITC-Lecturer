Dependency Inversion Principle

SOLID Principles - Part 5

Understanding the "D" in SOLID

High-level modules should not depend on low-level modules.
Both should depend on abstractions.

What is the Dependency Inversion Principle?

Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions.

  • High-level modules: Business logic, policies, complex algorithms
  • Low-level modules: Utility functions, data access, external services
  • Abstractions: Interfaces, abstract classes

The Two Parts of DIP

📈 Part 1

High-level modules should not depend on low-level modules. Both should depend on abstractions.

🎯 Part 2

Abstractions should not depend on details. Details should depend on abstractions.

Why Does DIP Matter?

🔧

Flexibility

Easy to swap implementations

🧪

Testability

Simple to mock dependencies

🏗️

Maintainability

Loose coupling between modules

📈

Scalability

Easy to extend functionality

The Traditional Approach

❌

Let's see what happens when we violate the DIP...

// High-level module depends directly on low-level modules class PaymentService { private stripeProcessor = new StripePaymentProcessor(); private paypalProcessor = new PaypalPaymentProcessor(); makePayment(amount: number, type: string) { if (type === "stripe") { this.stripeProcessor.process(amount); } else if (type === "paypal") { this.paypalProcessor.process(amount); } } }

Problems with This Approach

  • 🔒 Tight Coupling: PaymentService is tightly bound to specific processors
  • 🧪 Hard to Test: Cannot easily mock payment processors
  • 📦 Difficult to Extend: Adding new processors requires modifying PaymentService
  • 🔄 Violates Open/Closed: Must modify existing code for new features
  • ⚡ Runtime Dependencies: All processors must be available at compile time

The DIP Solution

✅

Let's apply the Dependency Inversion Principle...

// Step 1: Create an abstraction interface PaymentProcessor { processPayment(amount: number): void; } // Step 2: High-level module depends on abstraction class PaymentService { constructor(private processor: PaymentProcessor) {} makePayment(amount: number): void { this.processor.processPayment(amount); } }

Implementing the Abstraction

Low-level modules now depend on the abstraction:

class StripePaymentProcessor implements PaymentProcessor { processPayment(amount: number): void { console.log(`Processed $${amount} using Stripe.`); } } class PayPalPaymentProcessor implements PaymentProcessor { processPayment(amount: number): void { console.log(`Processed $${amount} using PayPal.`); } } class ApplePayPaymentProcessor implements PaymentProcessor { processPayment(amount: number): void { console.log(`Processed $${amount} using ApplePay.`); } }

Using the DIP Solution

// Create specific implementations const stripeService = new PaymentService( new StripePaymentProcessor() ); const paypalService = new PaymentService( new PayPalPaymentProcessor() ); const applePayService = new PaymentService( new ApplePayPaymentProcessor() ); // Use them stripeService.makePayment(100); paypalService.makePayment(200); applePayService.makePayment(300);

Dynamic Usage

The real power comes from dynamic processor selection:

// Array of different processors const processors: PaymentProcessor[] = [ new StripePaymentProcessor(), new PayPalPaymentProcessor(), new ApplePayPaymentProcessor() ]; // Process payments with each processor processors.forEach(processor => { const service = new PaymentService(processor); service.makePayment(100); }); // Output: // "Processed $100 using Stripe." // "Processed $100 using PayPal." // "Processed $100 using ApplePay."

Before vs After

❌ Before (DIP Violation)

  • Direct dependencies
  • Hard to test
  • Difficult to extend
  • Tight coupling
  • Violates OCP

✅ After (DIP Applied)

  • Depends on abstractions
  • Easy to test with mocks
  • Simple to add new processors
  • Loose coupling
  • Follows OCP

Dependency Injection

DIP often works hand-in-hand with Dependency Injection

// Constructor Injection (most common) class PaymentService { constructor(private processor: PaymentProcessor) {} } // Method Injection class PaymentService { makePayment(amount: number, processor: PaymentProcessor) { processor.processPayment(amount); } } // Property Injection class PaymentService { processor: PaymentProcessor; setProcessor(processor: PaymentProcessor) { this.processor = processor; } }

Testing Benefits

DIP makes unit testing much easier:

// Mock implementation for testing class MockPaymentProcessor implements PaymentProcessor { public processedAmount: number = 0; processPayment(amount: number): void { this.processedAmount = amount; } } // Test const mockProcessor = new MockPaymentProcessor(); const service = new PaymentService(mockProcessor); service.makePayment(150); console.log(mockProcessor.processedAmount); // 150 // Test passes - we can verify behavior without external dependencies

Real-World Example: Database Access

// Abstraction interface UserRepository { save(user: User): Promise<void>; findById(id: string): Promise<User | null>; } // High-level module class UserService { constructor(private userRepo: UserRepository) {} async createUser(userData: any): Promise<User> { const user = new User(userData); await this.userRepo.save(user); return user; } } // Low-level implementations class MongoUserRepository implements UserRepository { ... } class PostgreSQLUserRepository implements UserRepository { ... } class InMemoryUserRepository implements UserRepository { ... }

Real-World Example: Logging

// Abstraction interface Logger { log(message: string): void; error(message: string): void; } // High-level module class OrderService { constructor(private logger: Logger) {} processOrder(order: Order): void { this.logger.log(`Processing order ${order.id}`); // ... business logic ... this.logger.log(`Order ${order.id} processed successfully`); } } // Low-level implementations class ConsoleLogger implements Logger { ... } class FileLogger implements Logger { ... } class CloudLogger implements Logger { ... }

Common Mistakes to Avoid

  • 🚫 Creating interfaces after implementations: Design abstractions first
  • 🚫 One-to-one interfaces: Don't create interfaces that only have one implementation
  • 🚫 Leaky abstractions: Don't expose implementation details in interfaces
  • 🚫 Over-abstracting: Not everything needs an interface
  • 🚫 Ignoring the Liskov Substitution Principle: Implementations must be truly substitutable

When to Apply DIP?

✅

Apply When

  • Multiple implementations exist
  • External dependencies
  • Testing is important
  • Future extensibility needed
❌

Don't Apply When

  • Simple, stable dependencies
  • Language built-in features
  • Over-engineering risk
  • Single, unlikely-to-change impl

DIP and Other SOLID Principles

  • 🔗 SRP: Abstractions have single responsibility
  • 🔗 OCP: Open for extension via new implementations
  • 🔗 LSP: Implementations must be substitutable
  • 🔗 ISP: Keep interfaces focused and minimal

Remember: SOLID principles work together to create maintainable, flexible code!
